Having made sure that the program is syntactically correct, we want to confirm that our context-sensitive grammar is also semantically correct, 
i.e. perform context-sensitive checks and interpret the meaning of the program at its' syntactic level.
VVPL is a statically typed language, which usually means that we perform context-sensitive checks at compile-time, but due to the fact that VVPL is an interpreted language,
the property of being statically typed means that we perform the semantic analysis before runtime.

We use symbol tables upon entering a new scope in order to perform context-sensitive checks. VVPL's use of lexical scoping eases the process of identifying a new scope since we can align the construction
and destruction of symbol tables with the occurrence of curly brackets.
We chose to implement two separate symbol tables: \code{SymbolTable} for variables and \code{FuncSymbolTable} for functions as the mappings and the functionality for these tables would differ.
Functionality differs as a function table does not need the attribute \code{outer} due to it only being used in the global scope, and it does not need the \code{assign} method because we do not support assigning a new function declaration to a function identifier.

\paragraph{Design choices in Scope Analysis}\mbox{}\\
Usually, a variable is not allowed to shadow another variable in an outer scope. We implement this by making the \code{define} method look recursively in all outer tables
to check if the definition is legal.
In functions however, variables can shadow other variables defined outside of the function. This lead to the design decision of initializing functions with a fresh symbol table that has no outer table
so that bodies in functions are completely isolated, having no contact to the domain outside of the function.

This design solution impacted the solution to the issue of functions only being able to be defined in the global scope as we can no longer identify global scope uniquely by checking if \code{outer==null}.
Therefore the new symbol table attribute \code{isGlobal} was introduced, and functions defined in other tables than this would lead to an error.

Another key issue was the addressing of \code{ReturnStmt}s whose occurrence is only allowed in a function declaration. One could think that it would suffice to check if the current block 
was a direct descendant from a \code{FunctionStmt} by checking if the symbol table had the attributes \code{isGlobal = false;} and \code{outer = null;}.
This would however not suffice since nested blocks of these blocks also would be allowed to contain \code{ReturnStmt}s.

A solution to see whether we were analysing a function declaration would be to traverse all outer tables untill a body of a function declaration was identified by checking \code{isGlobal = false;} and \code{outer = null;}.
This could potentially have a high time complexity and it would be a complex solution to a simple problem. Instead we introduced the global variable \code{is\_function\_env} that is set before analysing a block in \code{VisitFunctionStmt}. 
This way \code{VisitReturnStmt} returns an error if this variable is false:

\paragraph{Design choices in Type Analysis}\mbox{}\\
We have constructed a separate class for executing the type analysis. This class could have been merged with the class of ScopeAnalyzer (i.e. a SemanticAnalyzer) but SOLID principles such as the Single Responsibility Principle suggests that responsibilities should be delegated to each their class.
Therefore we build the symbol tables from scratch again in order to build a context-sensitive environment required for the type analysis, but we do not need to error handle scope issues since those have been handled already.
This results in the usage of a much simpler SymbolTable as well as a new FuncSymbolTable where all error handling is omitted.

For the type analysis, an enum \code{Type} class have been implemented. The types are self-explanatory, while \code{Type.UNKNOWN} we use for two different cases:
\begin{itemize}
    \item Functions that do not have a type declared are assumed to return null. In this context, \code{Type.UNKNOWN} represents the value null
    \item Upon encountering an error in the type analysis, we return this value, so that calls higher up the call stack knows that an error was made and has already been processed. This way we avoid reporting cascading errors.
\end{itemize}

Having that cleared out, we proceed a particularly challenging issue we encountered during the development of the type analyzer:
\begin{itemize}
    \item A function declaration must in all cases return the declared type. It cannot miss a return statement or return the wrong type.
\end{itemize}
Enforcing that a function is guaranteed to return the declared type in all cases require extra handling. The requirement can be subdivided into two requirements:

\begin{itemize}
    \item Return statements within a function must all return the declared type
    \item A function with a declared type must always guarantee to return no matter which branch it chooses to take
\end{itemize}
To tackle the first requirement we introduced the global variable \code{currentFuncReturnType} which is set equal to the declared type within the function declaration. This is done in \code{VisitFunctionStmt} before analysing the body:

if (functionStmt.typeToken != null) {
   currentFuncReturnType = convertVariableType(functionStmt.typeToken.type);
} else { currentFuncReturnType = Type.UNKNOWN; }
\end{lstlisting}
This way \code{VisitReturnStmt} enforces the first requirement by comparing \code{currentFuncReturnType} to the type of the returned expression, returning an error upon mismatch.

The second requirement of having a function with a declared type always return no matter which branch it chooses to take is also enforced in the statically typed language Java and is appropiately enforced in VVPL as well.
\code{VisitFunctionStmt} uses the helper function \code{alwaysReturns} for the task:
\begin{lstlisting}[language=java, caption={\texttt{VisitFunctionStmt}}]
if (functionStmt.typeToken != null && !alwaysReturns(functionStmt.body)) {
    VVPLController.error(...);
}\end{lstlisting}
\code{alwaysReturns} is a recursive function that evaluates whether a function with a declared type contains a return statement within all possible paths.
There are four cases to evaluate.
\begin{itemize}
    \item If a return statement occurs in a branch, this branch is guaranteed to return. This is the base case.
    \item An if-else statement is only guaranteed to return if both the then branch and the else branch returns.
    \begin{itemize}
        \item If the else branch is non-existant, the function can potentially skip the if-branch, therefore not returning.
    \end{itemize}
    \item A block statement (which also constitutes the body of a function) is only guaranteed to return if any statement within the block are guaranteed to return.
    \item Any other kind of statement cannot be guaranteed to return.
\end{itemize}

With the help of \code{currentFuncReturnType} and \code{alwaysReturns}, functions are always guaranteed to return, and all possible return values matches the declared type.
