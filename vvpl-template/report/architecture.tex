\subsubsection{Control flow}
The architecture of the VVPL interpreter follows a multi-stage pipeline closely aligned with the control flow recommended
in the project description. Each stage performs a distinct task and depends on the successful completion of the previous stage.
If errors are detected in a stage, subsequent stages are not executed.
An overview of the control flow is depicted on figure \ref{fig:architecture}, which shows how different
components are coordinated during interpretation.
\begin{figure}[H]
\centering
\includegraphics[width=0.7\textwidth]{architecture.png}
\caption{An illustration of the interpreters control flow}
\label{fig:architecture}
\end{figure}

At the center of both the figure and the architecture is the \texttt{VVPLController} class, which orchestrates the
entire interpretation process.
It does this by invoking the classes in the order depicted on the figure and if all things go well
it outputs the result of the program's execution leading to a happy developer. Otherwise it
outputs all error messages encountered at the failing stage. The crying developer in the figure 
is hopefully upset because of their buggy program and not the quality of our interpreter.

% Dette afsnit kan måske godt cuttes fra. Hvis vi gør det tilføj eventuelt "Controller recieves VVPL source file" til overstående.
The controller recieves the VVPL source file as input and passes this to the Scanner, which detects any
lexical errors as it translates the stream of characters into a sequence of tokens.
These tokens are passed to the Parser, which by utilizing the grammar rules assembles these tokens into syntactic units
and builds the abstract syntax tree (AST).
Once a valid AST has been obtained, the controller initiates semantic analysis in two separate stages.
The \texttt{ScopeAnalyzer} checks declaration and scope related constraints and, only if these checks succeed, the
\texttt{TypeAnalyzer} verifies type correctness.
Finally, the \texttt{Interpreter} traverses the AST and executes the program.



Importantly, none of the individual components communicate directly with eachother. 
As depicted by the arrows in figure \ref{fig:architecture}, they are each invoked by the controller and report their results back to the controller.
In this way all interaction is mediated by the controller, which avoids tight coupling between the stages.
The design promotes modularity and seperation of concerns, where each component is responsible for a distinct phase of the interpretation process.
The components can focus on their specific responsibility without having to concern themselves with the details of the other components.
This makes the system both easier to extend and test.




\subsubsection{Error handling}
The architecture naturally supports structured error handling.
Each of the stages identify errors and notify the \texttt{VVPLController}, which in turn is responsible for 
handling how these errors are stored and reported to the user.
This seperation decouples error \emph{detection} from error \emph{reporting}.

Errors are sent to the controller with their line number, an error category from the \texttt{ErrorTypeStrings} class
and a description. When this happens the \texttt{hadError} flag in the controller is set.
The controller checks this flag between stages and terminates if any error was detected.
Halting the interpreter as soon as a single stage fails is part of a fail fast strategy preventing later stages from operating 
on invalid data which would otherwise cause a cascade of confusing and possibly misleading errors.
At the same time each individual stage is designed to detect as many errors as possible before returning
control to the \texttt{VVPLController} in order to provide the user with as comprehensive a report of their errors as possible. Only the final \verb|Interpreter| visitor aborts the program immediatly upon an error.

Reported errors are stored as structured \texttt{ErrorMessage} objects rather than plain strings.
The line number, error type and message is stored in seperate fields which allows for easy post-processing.
In particular, errors can be sorted by their occurence in the program by having the \texttt{ErrorMessage} class
implement the \texttt{Comparable} interface, ensuring the user receives feedback in a logical and actionable order.

\subsubsection{Traversing the AST with the Visitor pattern}

After lexing, the parser outputs an AST as an intermediate representation. 
Abstractly representing our source code allows us to implement the methods necessary for translating the identified tokens of the grammar into program output.
Ideally, our AST is abstracting away language specific details and carry just enough information to maintain the semantic meaning of the program allowing us 
to check for semantic errors, interpret its content or, if necessary in the future, do optimization.

The program structure is then represented by nodes, each implemented as a polymorphic subclass of the \verb|Expr| or \verb|Stmt| superclass.
This allows us to gradually unpack the semantic meaning following the given order and rules of the grammar.
During our traversal, we want to perform specific operations on each node, based on the current stage of the semantic analysis or the interpretation, and instead of implementing all these different behaviours associated with each stage directly in methods on the classes themselves, we do so by implementing a \verb|Visitor| interface for each distinct traversal. 

The visitor pattern promotes openness for extension and separation of responsibility by separating the storage of data from the use of that data, 
allowing our interpreter to scale in size and functionality more easily. 
Now, AST nodes are responsible only for representing program structure, while the responsibility of the concrete behavior is implemented in a \textit{visitor} of the node.
%Now, we delegate the responsibility of the concrete implementation to a \textit{visitor} of a class, and not the class itself. - Har ændret til overstående /Lucas
The key facet is, that we can add one 
\verb|accept()| method to each AST node class, then use this for as many different implementations of visitors as we want, essentially allowing us to implement different 
behaviour on different traversals of the tree, depending on our goal with that traversal.

This utilizes a \textit{double dispatch} where the operation executed depends on both the type of visitor class and within that visitor, the type of node to call \verb|accept| upon.
For example, the evaluation of the node \verb|CallExpr| in the visitor class \verb|ScopeAnalyzer| is concerned about the correct binding of variables while in  the \verb|TypeAnalyzer| visitor, \verb|CallExpr| is concerned about the correct type of arguments used.
If we have ran the the two semantic stages beforehand, and a statement is without errors e.g \verb|add(multiply(2 2) 4);|, the AST will then be evaluated by the \verb|Interpreter| visitor (Figure \ref{fig:ast-visitor}).
% Måske kan man smide ordet "reusability" ind eftersom hun selv skriver: 
%Try to explain the development choices you made taking into account important properties, such as reusability and performance.
The double dispatch of the visitor pattern does introduce an amount of overhead, but in turn helps us greatly with the reusability of operations, separation of concerns and the 
open-closed principle in regards to multiple ways of traversing the tree. Another downside is that if the structure of the tree changes, i.e new node classes are introduced as 
the language evolves, we would have to update all of the existing visitors with the method to handle the new node.
