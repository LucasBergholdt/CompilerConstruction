An essential part of making a programming language usable includes having a sensible error handling.
Clear error messages help users understand what went wrong in their program and how to fix it.
To facilitate this, we perform error handling in all parts of the interpreter.

At the center of the error handling is the \texttt{VVPLController} class which functions as a centralized hub for
reporting errors. This design decouples the error \emph{detection} from the error \emph{reporting}.
Each component such as the scanner or parser is responsible for identifying errors and notifying the
\texttt{VVPLController} class which in turn is responsible for handling how these errors are stored
and reported to the user.

This interplay between the classes is facilitated by the \texttt{error} method in the controller.
\begin{lstlisting}[language=java]
public static void error(int line, String errorType, String message) {
    hadError = true;
    errorMessages.add(new ErrorMessage(line, errorType, message));
}
\end{lstlisting}

This method takes in the line where the error occured, the type of error and the error message we are reporting to the user. 
The error type is one of the different errors from the \texttt{ErrorTypeStrings} class, which allows us to categorize the errors.
The method firstly sets the \texttt{hadError} flag, which signals that the current stage of compilation has failed.
After each stage of the interpreter pipeline, the controller checks this flag. If an error has been registered the pipeline stops.
Halting the interpreter as soon as a single stage fails is part of a fail fast strategy that prevents later stages from operating 
on invalid data which would cause a cascade of confusing and possibly misleading errors.

While the pipeline stops between stages, each individual stage is designed to detect as many errors as possible before terminating,
providing the user with a comprehensive report of their errors in that stage.
This gives the user a more complete overview of issues which decreases time spent debugging by
reducing the number of compiles needed to find and fix all errors in the program.

After setting the \texttt{hadError} flag the error is added to the errorMessages list which stores all the errors.
This is a list of \texttt{ErrorMessage} objects:
\begin{lstlisting}[language=java]
private static List<ErrorMessage> errorMessages = new ArrayList<>();
\end{lstlisting}

The \texttt{ErrorMessage} class stores errors as structured data rather than just plain strings.
It stores the line number, error type and message in seperate fields which allows for easy post-processing.
Specifically this allows for sorting the 
errors by line number such that the user receives a logical and actionable list of issues in the order they appear in the code. 
This is achieved by having \texttt{ErrorMessage} implement the \texttt{Comparable} interface allowing the controller to sort the list with
the \texttt{sort} method from the Collections class.
The class also overrides the \texttt{toString} method such that the error messages can easily be reported to the
user in the format: \texttt{<error-type>, line <lineNo> <message>}.

\paragraph{Lexical error handling in the Scanner}\mbox{}\\
The \texttt{Scanner} is the first component to utilize this centralized error handling.
When it encounters a character or character sequence that does not conform with the language, 
it calls the controller's \texttt{error} method. A common example is
finding a character that is not part of the language such as '\$'.
This is handled in the default branch of the \texttt{scanToken} method:
\begin{lstlisting}[language=java]
private void scanToken() {
    char c = advance();
    switch (c) {
        // ... cases for valid characters
        default:
            if (isDigit(c)) {
                number();
            } else if (isAlpha(c)) {
                identifier();
            } else {
                VVPLController.error(line, ErrorTypeStrings.SCAN_ERROR, "Unexpected character.");
            }
    }
}
\end{lstlisting}

A deliberate design choice here is that the scanner does not halt after finding an error. Instead it simply reports the error and
proceeds to the next character, attempting to tokenize the rest of the file. This allows the scanner to report all
lexical erros in a single pass, rather than informing the user about the errors one by one.

\paragraph{Syntactic error recovery in the Parser}\mbox{}\\
While the scanner can often recover from errors by simply advancing, handling errors in the parser is more involved.
The parser should be robust in the face of syntax errors such that it does not crash or hang.
Invalid code is valid input for a parser since one of its key responsibilities is to teach the user what
valid syntax looks like.
%Måske omskriv til: (invalid code = valid input taget fra bogen)
%A parser must be able to handle invalid code gracefully as one of its key responsibilities
%is to guide the user in writing syntactically correct programs.
A single syntax error like a missing parenthesis may confuse the parser and cause it to report a long cascade
of pseudo-errors that don't indicate another real problem in the code. 
We should strive to report only errors that are caused by the user's invalid syntax and not by the parser's own
confusion after encountering an error.

To support both reporting as many distict errors as possible while also filtering out those who are simply a side-effect
of another error we have implemented the more sophisitcated error recovery strategy known as \emph{panic mode}.

\paragraph{Panic mode and synchronization}\mbox{}\\
When the parser detects an error it enters panic mode.
At this point the parser knows that at minimum one token is unexpected in the
current state of applying a production rule from the grammar and that the parser's internal state and the remaining
token stream may no longer be aligned. Before parsing can continue, the parser must realign its state with the upcoming tokens
such that the next token matches the expected token in the rule being parsed.

This is accomplished through synchronization. 
The idea is to choose a specific grammar rule as synchronization point that is safe to restart from and 
to discard tokens until a token that is valid at this synchronization point is encountered.
%The parser can fix its state by jumping out of any nested state to the synchronization point.
%Thereby synchronizing the token stream by discarding tokens until encountering a token that is allowed at the synchronization point.
Our chosen synchronization point follows the common decision of choosing to synchronize between statements.

The implications of this approach is that any real syntax errors hiding inside the discarded tokens will not be reported.
However, this is an acceptable tradeoff for avoiding falsely reporting cascaded errors in the discarded tokens that are
simply a side effect of the initial error.


\paragraph{Synchronizing via exceptions}\mbox{}\\
In a recursive descent parser like ours the parser's state is not explicitly stored but instead tracked with the call stack. 
So to reset the parser's state we need to clear out the call frames on the stack.
We achive this by using Java exceptions. Encountering a syntax error triggers a \texttt{ParseError} exception, which
unwinds the stack until it is caught in the \texttt{parse} loop between statements.

The exception is triggered through the parser's \texttt{error} method, which informs the controller about the error and produces the exception:
\begin{lstlisting}[language=java]
private ParseError error(Token token, String message) {
    VVPLController.error(token.line, ErrorTypeStrings.PARSE_ERROR, message);
    return new ParseError();
}
\end{lstlisting}

The exception itself is just a simple class:
\begin{lstlisting}[language=java]
private static class ParseError extends RuntimeException {}
\end{lstlisting}

When a \texttt{ParseError} is thrown, the top-level loop in \texttt{parse} catches it and invokes the \texttt{syncrhonise} method.
This method discards tokens until reaching a token that can begin a new statement.
The \texttt{synchronise} method can be seen in its full glory below. It mainly conists of just a simple switch statement in a loop.
We are also returning if we have just discarded a semicolon as this is a good indication, that a new statement is likely to start.
%TODO: Skal synchronise method vises i sin helhed her?
\begin{lstlisting}[language=java]
private void synchronise() {
    advance(); // Discard the problematic token that triggered the error

    while (!isAtEnd()) {
        if (previous().type == SEMICOLON) return;

        switch (peek().type) {
            case FUNCTION:
            case VAR:
            case IF:
            case WHILE:
            case PRINT:
            case LEFT_BRACE:
            case RETURN:
                return;
            
            default:
                advance(); // Discard token and continue
                break;
        }
    }
}
\end{lstlisting}

The \texttt{error} method is also integrated into \texttt{consume}, supporting reusability and enabling consistent
syntax checking throughout the parser:
\begin{lstlisting}[language=java]
private Token consume(TokenType type, String message) {
    if (check(type)) {
        return advance();
    } else {
        throw error(peek(), message);
    }
}
\end{lstlisting}


This parsing strategy ensures that the parser reports only genuine syntax erros, recovers cleanly and avoids polluting
the error output with misleading cascading errors.
